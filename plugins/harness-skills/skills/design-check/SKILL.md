# Design check

Rules reviewers kept raising. Go through every one before the first line of code and again before the PR; fix what fails, or write down in the PR why it stays.

- **Dependencies point one way.** A base module that must import a module built on top of it means the design is upside down. Once you start adding type-only import stubs, lazy imports or protocol shells to dodge a cycle, stop and turn the direction around. A mixin that needs members of its host is better as a module function that takes the host as an argument.
- **A shared guard lives at one entry point.** Put the check once in the base class's public method (template method) instead of copying it into every subclass. If you need a meta-test that checks no copy was missed, the copying is the cost.
- **Design docs move with the code, in the same PR.** When a decision changes, change its line in the ADR or spec in that PR. Every place that repeats a number, list or name (overview, tables, QA notes, API descriptions) shows the same value.
- **Fix every copy of the cause.** Before calling a fix done, search the repo for the same pattern (the call, the literal, the copied branch) and fix each hit or list the ones left in the PR body. Write the ones left into the issue the PR closes as well, so a leftover is not filed again as a new bug. Reviewers find the sibling call site the fix skipped more often than a flaw in the fix itself.
- **Find the paths you did not edit.** Before the first line of code, list three things and keep the list in the PR: every other feature that reads the value or stored shape you change (search the paired repo too), every other entry point to the same action (single and bulk, the parent's delete, editor and viewer, draft and deployed copy), and each permission check, row filter or mask the existing path goes through. Run the same test against each entry point, so a guard added to one fails for the others. A blocker is more often a path the change never touched than a flaw in the path it did.
- **A fake of another service answers only what the real one can.** When a test double (a mock route, a stub server, a fixture handler) gains a rejection, a status code or a permission outcome, read the real service's code on its fetched default branch and match the condition, not only the response shape. A rule the fake does not imitate is written in the PR as not imitated; a response the real service can never send is removed.
- **A failed, empty or still-loading read never shows a plausible value.** No `0`, unfiltered total, empty collection or stale value where the truth is "unknown": show the error, the empty state or the loading state. When two paths compute the same figure (server and browser, editor and viewer), give them the same rule for a missing value.
- **Tests encode only the guarantees the code gives.** No docstring or assertion claims a guarantee that does not exist. If a race window remains, say it was narrowed, not closed. Prefer behaviour tests over meta-tests that inspect the code's shape. For each guard, limit or branch the change adds, delete that line and run the tests: if nothing fails, the test is missing. A time limit is asserted relative to a baseline or as an operation count, never as absolute seconds, which fail under a loaded suite.
- **A replaced path keeps what the old one enforced.** When a new route, parser or code path takes over from an old one, list the old path's limits, permission checks, cleanup branches and error mapping, and carry each over or say in the PR why it goes. Test a retry with the state the first attempt left behind, and a unit or coordinate conversion with a non-default unit.
- **A number in the PR or ADR is measured or counted.** "N call sites", "under 1 s", "all paths" come from a command you ran (`rg -c`, a timing, a test count); otherwise drop the number.
- **Check races with delete and reindex first.** A compensating delete after the write can remove live data. Check before writing and skip the write when the target is gone; when the store has no conditional write, document the window.
- **Say which layer owns each limit and deadline.** For example, count and byte limits belong to the parser, time limits to the caller. Record the boundary in the ADR, and record "none" explicitly when there is no limit.
- **A design review sorts findings into savings, decisions and local trims.** Structural cleanups / items that need a decision (with an ADR) / local shortenings, each with a line count or cost in numbers, so the reader does not have to re-rank them.
